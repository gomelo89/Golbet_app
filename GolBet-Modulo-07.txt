Objetivo del módulo
GolBet por fin sabe QUIÉN la usa. Este módulo integra ASP.NET Core Identity: registro de apostadores con 100.000 FutCoins de bienvenida, login/logout con cookies, los roles Admin y Apostador, el nombre y el saldo visibles en el navbar y el [Authorize] pagando de una vez la deuda de seguridad declarada en los Módulos anteriores. La entidad Bet se completa con su apostador (UserId) y el índice único que blinda la regla «misma selección, una sola vez».
Al terminar, GolBet tendrá todo lo necesario para que el Módulo 8 implemente las apuestas: partidos gestionables, usuarios con saldo, y la tabla Bets conectada a quienes apuestan.
Duración estimada: 2 sesiones de clase.
1. Conceptos previos
La AUTENTICACIÓN responde «¿quién eres?» (login); la AUTORIZACIÓN responde «¿qué puedes hacer?» (roles, [Authorize]). Son dos preguntas distintas que suelen confundirse,Identity resuelve ambas, pero el orden del pipeline las separa: UseAuthentication identifica, UseAuthorization decide.
ASP.NET Core Identity: el framework oficial de ASP.NET Core para gestionar usuarios. Trae las tablas (AspNetUsers, AspNetRolesy las 6 que aparecieron en el diagrama de entidad-relación), el hash seguro de contraseñas, los managers (UserManager, SignInManager, RoleManager) y la emisión de cookies. Lo que NO trae: pantallas, las construiremos nosotros.
Cookies y claims: tras un login exitoso, el servidor emite una COOKIE cifrada con la identidad del usuario (id, nombre, roles y sus claims). El navegador la reenvía en cada petición, y UseAuthentication la convierte en el objeto User disponible en controllers y vistas. Por eso no hay que «consultar la sesión» en cada página: la identidad viaja sola.
Hash de contraseñas: las contraseñas explícitas JAMÁS se guardan, se guarda un HASH irreversible. Ni el administrador ni la base de datos conocen la contraseña de nadie; el login re-calcula el hash de lo tecleado y compara. Verlo en SSMS (columna PasswordHash) es una capa de seguridad.
Roles: grupos con permisos. GolBet usa dos: Admin (gestiona equipos, partidos y cierres) y Apostador (apuesta). El Anónimo no es un rol: es la ausencia de identidad, puede mirar la cartelera y nada más.
[Authorize] sobre un controller o acción exige identidad; [Authorize(Roles = "Admin")] exige además el rol. Su contraparte [AllowAnonymous] abre excepciones.

¿Por qué los modelos de Register/Login van en GolBet.Web/Models y no en Services/DTOs? Porque no cruzan capas: nacen en un formulario y mueren en el AccountController, que habla directamente con los managers de Identity, no hay servicio de negocio de por medio. Un objeto que solo existe para alimentar una vista se llama ViewModel, y vive en la capa de presentación. Los DTOs de Services son los que VIAJAN entre capas.

4. AppUser, la Bet completa y el DbContext de Identity
4.1 AppUser: el usuario del dominio
// GolBet.Entities/AppUser.cs
using System.ComponentModel.DataAnnotations;
using Microsoft.AspNetCore.Identity;
namespace GolBet.Entities;
/// <summary>
/// Application user. Extends IdentityUser with GolBet-specific data.
/// Note: cannot inherit AuditableEntity (C# single inheritance);
/// Identity brings its own string Id.
/// </summary>
public class AppUser :IdentityUser
{
[MaxLength(100)]
public string FullName{ get; set; } = null!;
/// <summary>Virtual currency balance (FutCoins).</summary>
public decimal Balance { get; set; }
public ICollection<Bet> Bets { get; set; } = new List<Bet>();

La salvedad anunciada desde el Módulo 2, cumplida: AppUser hereda de IdentityUser (que trae Id string, Email, PasswordHash y todo el equipaje de Identity) y por eso NO puede heredar de AuditableEntity, C# no permite doble herencia de clases. Consecuencias: su PK es string (nvarchar(450), GUIDs como texto), y no recibe estampas de auditoría automáticas (Identity registra lo suyo). Solo agregamos lo que GolBet necesita: el nombre completo, el saldo de FutCoins, y la colección de apuestas.
4.2 Bet se completa: el apostador
Las dos propiedades que la Bet esperaba desde el Módulo 2:
// GolBet.Entities/Bet.cs(agregar)
public string UserId{ get; set; } = null!;   // FK -> AspNetUsers (string PK)

Nota el tipo de la FK: string, no int porque el tipo de una FK debe coincidir con la PK a la que APUNTA (AspNetUsers.Id es string), no con la PK propia. Bet queda con la particularidad de PK int (heredada de AuditableEntity) y FK string hacia usuarios: perfectamente válido.

protected override void OnModelCreating(ModelBuildermodelBuilder)
{
base.OnModelCreating(modelBuilder);   // FIRST: Identity maps its 6 tables here
// Team names must be unique (case- and accent-insensitive)
modelBuilder.Entity<Team>()
.Property(t => t.Name)
.UseCollation("SQL_Latin1_General_CP1_CI_AI"); //Esta parte me indica el Sensitive Case
modelBuilder.Entity<Team>()
.HasIndex(t => t.Name)
.IsUnique();
// Double relationship Match -> Team: convention cannot resolve it
modelBuilder.Entity<Match>()
.HasOne(m => m.HomeTeam)
.WithMany()
.HasForeignKey(m => m.HomeTeamId)
.OnDelete(DeleteBehavior.Restrict);
modelBuilder.Entity<Match>()
.HasOne(m => m.AwayTeam)
.WithMany()
.HasForeignKey(m => m.AwayTeamId)
.OnDelete(DeleteBehavior.Restrict);
// A match with bets cannot be deleted
modelBuilder.Entity<Bet>()
.HasOne(b => b.Match)
.WithMany(m => m.Bets)
.OnDelete(DeleteBehavior.Restrict);
// ---- Identity additions ----
// Bet -> User: a user's bets cannot be destroyed by deleting the user
modelBuilder.Entity<Bet>()
.HasOne(b => b.User)
.WithMany(u => u.Bets)
.HasForeignKey(b => b.UserId)
.OnDelete(DeleteBehavior.Restrict);
// Business rule #3: same user cannot repeat the same pick on a match
modelBuilder.Entity<Bet>()
.HasIndex(b => new { b.MatchId, b.UserId, b.Pick })
.IsUnique();
// FutCoins balance precision (up to 9,999,999,999.99)
modelBuilder.Entity<AppUser>()
.Property(u => u.Balance)
.HasPrecision(12, 2);
}
// ---- Automatic audit timestamps ----
public override Task<int> SaveChangesAsync(CancellationTokencancellationToken = default)
{
var utcNow = DateTime.UtcNow;
foreach (var entry in ChangeTracker.Entries<AuditableEntity>())
{
switch (entry.State)
{
case EntityState.Added:
entry.Entity.CreatedDate = utcNow;
break;
case EntityState.Modified:
entry.Entity.ModifiedDate = utcNow;
// CreatedDate must never change after creation
entry.Property(e => e.CreatedDate).IsModified = false;
break;
}
}
return base.SaveChangesAsync(cancellationToken);
}
}
}
Tres piezas para leer con cuidado: (1) la herencia cambia a IdentityDbContext<AppUser>, con eso, las 6 tablas de Identity entran al modelo usando AppUser como usuario; (2) el base.OnModelCreating(modelBuilder) DEBE ser la primera línea, ahí Identity mapea sus tablas y claves; omitirlo produce el error «IdentityUserLogin<string> requires a primarykey» (ya tiene fila en la tabla de errores); (3) el índice único compuesto (MatchId, UserId, Pick) ES la regla de negocio #3 de la Guía convertida en constraint físico: selecciones distintas en el mismo partido sí, la misma selección repetida no y lo garantiza la base de datos aunque un bug se colara por las capas superiores.

5. Program.cs: registrar Identity y activar el pipeline
// GolBet.Web/Program.cs
// --- after AddDbContext ---
builder.Services.AddIdentity<AppUser, IdentityRole>(options =>
{
// Academic-friendly password policy (production would be stricter)
options.Password.RequiredLength = 6;
options.Password.RequireNonAlphanumeric = false;
options.Password.RequireUppercase = false;
options.Password.RequireDigit = true;
options.User.RequireUniqueEmail = true;
})
.AddEntityFrameworkStores<AppDbContext>();
builder.Services.ConfigureApplicationCookie(options =>
{
options.LoginPath = "/Account/Login";           // anonymous hitting [Authorize]
options.AccessDeniedPath = "/Account/AccessDenied";  // wrong role
});
// --- in the pipeline, before app.UseAuthorization() ---
app.UseAuthentication();   // who are you?  (reads the cookie, builds User)
app.UseAuthorization();    // may you do this?  (evaluates [Authorize])
El orden del pipeline importa y es examen seguro: UseAuthentication va ANTES de UseAuthorization, primero se establece quién eres (leyendo la cookie), después se decide si puedes. Invertirlos produce el síntoma desconcertante de «estoy logueado pero todo me redirige al login». La plantilla MVC ya trae UseAuthorization; solo hay que agregar UseAuthentication encima. Y las dos rutas de la cookie separan los dos fracasos: sin identidad → LoginPath; con identidad pero sin rol → AccessDeniedPath.

private static async Task SeedIdentityAsync(
RoleManager<IdentityRole> roleManager,
UserManager<AppUser> userManager)
{
// Roles (idempotent)
foreach (var role in new[] { AdminRole, BettorRole })
{
if (!awaitroleManager.RoleExistsAsync(role))
await roleManager.CreateAsync(new IdentityRole(role));
}
// Admin user (idempotent)
if (await userManager.FindByEmailAsync("admin@golbet.com") is null)
{
var admin = new AppUser
{
UserName = "admin@golbet.com",
Email = "admin@golbet.com",
FullName = "AdministradorGolBet",
Balance = 0m,              // admins manage, they do not bet
EmailConfirmed = true
};
await userManager.CreateAsync(admin, "Admin123*");
await userManager.AddToRoleAsync(admin, AdminRole);
}
}
}

7.2 AccountController
// GolBet.Web/Controllers/AccountController.cs
using GolBet.Entities;
using GolBet.Repositories.Data;
using GolBet.Web.Models;
using Microsoft.AspNetCore.Authorization;
using Microsoft.AspNetCore.Identity;
using Microsoft.AspNetCore.Mvc;
namespace GolBet.Web.Controllers;
public class AccountController : Controller
{
private const decimal WelcomeBalance = 100_000m;   // business rule #7
private readonlyUserManager<AppUser> _userManager;
private readonlySignInManager<AppUser> _signInManager;
public AccountController(
UserManager<AppUser> userManager,
SignInManager<AppUser> signInManager)
{
_userManager = userManager;
_signInManager = signInManager;
}
// GET /Account/Register
public IActionResultRegister() => View(new RegisterViewModel());
// POST /Account/Register
[HttpPost, ValidateAntiForgeryToken]
public async Task<IActionResult> Register(RegisterViewModel model)
{
if (!ModelState.IsValid) return View(model);
var user = new AppUser
{
UserName = model.Email,
Email = model.Email,
FullName = model.FullName,
Balance = WelcomeBalance      // 100,000 FutCoins on sign-up
};
var result = await _userManager.CreateAsync(user, model.Password);
if (!result.Succeeded)
{
foreach (var error in result.Errors)
ModelState.AddModelError(string.Empty, error.Description);
return View(model);
}
await _userManager.AddToRoleAsync(user, DbSeeder.BettorRole);
await _signInManager.SignInAsync(user, isPersistent: false);
TempData["Success"] = $"¡Bienvenido a GolBet, {user.FullName}! " +
"Tienes 100.000 FutCoins para empezar.";
return RedirectToAction("Index", "Matches");
}
// GET /Account/Login
public IActionResultLogin() => View(new LoginViewModel());
// POST /Account/Login
[HttpPost, ValidateAntiForgeryToken]
public async Task<IActionResult> Login(LoginViewModel model)
{
if (!ModelState.IsValid) return View(model);
var result = await _signInManager.PasswordSignInAsync(
model.Email, model.Password, model.RememberMe,
lockoutOnFailure: false);
if (!result.Succeeded)
{
ModelState.AddModelError(string.Empty,
"Correo o contraseña incorrectos.");
return View(model);
}
return RedirectToAction("Index", "Matches");
}
// POST /Account/Logout
[HttpPost, ValidateAntiForgeryToken]
[Authorize]
public async Task<IActionResult> Logout()
{
await _signInManager.SignOutAsync();
return RedirectToAction("Index", "Home");
}
// GET /Account/AccessDenied
public IActionResultAccessDenied() => View();
}
¿Por qué este controller usa los managers directamente, sin capa de servicios? Pregunta legítima que algún estudiante hará. Respuesta: UserManager y SignInManager YA SON la capa de servicios de la autenticación — un framework completo con su lógica (hash, validación, cookies). Envolverlos en un IAccountService que solo delegue sería abstracción sin contenido. La regla de GolBet («los controllers no tocan el DbContext») sigue intacta: aquí nadie toca el contexto — se habla con managers. Cuando el registro involucre lógica de negocio PROPIA (en el proyecto final: bonos de referido, por ejemplo), ahí sí nacería el servicio.
Puntos calientes del código: WelcomeBalance = 100_000m es la regla de negocio #7 (el guion bajo es separador de miles de C# — pura legibilidad); los errores de CreateAsync (contraseña débil, correo repetido) se vuelcan al ModelState y aparecen en el summary — mismo canal que todas las validaciones (vienen en inglés por defecto; traducirlos es el reto del módulo); el login falla con mensaje GENÉRICO a propósito — «correo o contraseña incorrectos» no revela cuál de los dos, para no regalarle a un atacante la confirmación de qué correos existen; y Logout es POST con [ValidateAntiForgeryToken], no un enlace GET — cerrar sesión cambia estado, misma regla de los verbos del Módulo 6.

Dos granularidades, una decisión por controller: TeamsController se protege a nivel de CLASE (toda la gestión de equipos es de Admin); MatchesController se protege por ACCIÓN, porque conviven lo público (Index, Detail) y lo administrativo. Usar la constante IdentitySeeder.AdminRole en lugar del string "Admin" paga dividendos ya: un typo no compila.

9. Verificación y cierre
El recorrido completo, en orden: (1) Anónimo: la cartelera y el detalle abren; el navbar ofrece Iniciar sesión / Registrarse; no se ven Equipos ni botones de gestión; (2) Registro: crear una cuenta nueva → redirige a la cartelera con la bienvenida y el navbar muestra nombre y 💰 100.000 FutCoins. (3) El apostador NO ve botones de gestión, y /Teams a mano → Acceso denegado. (4) Cerrar sesión → ingresar como admin@golbet.com / Admin123* → aparecen Equipos, + Nuevo partido y Editar; sin saldo en el navbar. (5) En SSMS: AspNetUsers con FullName, Balance y PasswordHash (hash, no contraseña), AspNetRoles con los 2 roles, AspNetUserRoles conectándolos, y Bets con su columna UserId y el índice único IX_Bets_MatchId_UserId_Pick.

Errores comunes de este módulo
Síntoma
Causa probable
Solución
"The entity type 'IdentityUserLogin<string>' requires a primary key" al migrar
Falta el base.OnModelCreating(modelBuilder) al inicio del OnModelCreating
Debe ser la PRIMERA línea del método: ahí Identity mapea sus tablas y claves.
Estoy logueado pero todo redirige al login
UseAuthentication falta o quedó DESPUÉS de UseAuthorization
Orden obligatorio: UseAuthentication primero (quién eres), UseAuthorization después (qué puedes).
Al dar clic en páginas de Admin redirige a /Identity/Account/Login y da 404
No se configuró ConfigureApplicationCookie y rige la ruta por defecto de Identity
FijarLoginPath = /Account/Login y AccessDeniedPath = /Account/AccessDenied.
"Unable to resolve service for type 'UserManager<AppUser>'"
Faltó el AddIdentity en Program.cs (o quedó después del Build)
El bloque AddIdentity(...).AddEntityFrameworkStores<AppDbContext>() va antes de builder.Build().
El registro falla con mensajes en inglés de contraseña
No es un error: es la política de contraseñas de Identity actuando
Ajustar options.Password en el AddIdentity, o traducir los mensajes (reto del módulo).
El saldo no aparece o la parcial lanza NullReferenceException
Falta el @inject de los managers en _LoginPartial, o se usa User.Identity.Name en vez del AppUser
Copiar la cabecera completa de la parcial: los dos @using y los dos @inject.
Migración falla: "column 'UserId' cannot be null" (o similar) sobre Bets
Había filas de prueba en Bets antes de agregar la FK obligatoria
Borrar esas filas (DELETE FROM Bets) y re-ejecutarUpdate-Database — o borrar la BD completa y dejar que el seeder la reconstruya.
Tras registrarme, /Teams me deja entrar (¡no debería!)
El [Authorize] se olvidó en algún controller o acción de escritura
Repasar la lista: TeamsController a nivel de clase; en MatchesController las 5 acciones de escritura.
